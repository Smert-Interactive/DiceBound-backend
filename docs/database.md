# База данных и Prisma Migrate

Backend использует PostgreSQL и Prisma ORM 7. Миграциями управляет только
Prisma Migrate. Подключение для CLI, seed и приложения задаёт `DATABASE_URL`.
Отдельный PostgreSQL-сервер или новая база для перехода не требуются.

## Файлы реализации

```text
prisma/
  schema.prisma
  migrations/
    migration_lock.toml
    001_users/migration.sql
    002_game_systems/migration.sql
    003_characters/migration.sql
    004_character_shares/migration.sql
  seed.mjs
  seeds/builtin-systems.json
  manual-rollback/*.down.sql
test/database/
  seed-contract.test.mjs
  model.test.mjs
```

`schema.prisma` описывает шесть моделей: User, GameSystem, SheetSchema,
Character, CharacterVersion и CharacterShare. Имена полей клиента — camelCase;
`@map` / `@@map` сохраняют имена колонок и таблиц в snake_case.
UUID создаёт PostgreSQL через `gen_random_uuid()`, даты хранятся как
`timestamptz`, структуры листов и данные персонажей — как JSONB.

Триггеры, функции, CHECK и уникальный индекс `lower(btrim(email))` поддерживаются
в SQL миграций. У `email` намеренно нет обычного `@unique`: он не заменяет
уникальность нормализованного выражения. Поиск для авторизации должен учитывать
нормализацию email. Поля `source` и `permission` остаются PostgreSQL `text` с
CHECK, а не переводятся в новые enum-типы.
`updated_at` обновляет триггер БД; `@updatedAt` в моделях не используется.

## Команды

| Команда | Назначение |
| --- | --- |
| `npm run db:validate` | Проверить Prisma-схему без подключения к БД |
| `npm run db:generate` | Сгенерировать Prisma Client без подключения к БД |
| `npm run db:migrate:dev -- --name <name>` | Создать и применить новую миграцию в своей среде разработки |
| `npm run db:migrate:deploy` | Применить готовые миграции |
| `npm run db:migrate:status` | Проверить историю и ожидающие миграции |
| `npm run db:seed` | Добавить или проверить встроенные системы и схемы |
| `npm run test:seed` | Проверить seed-контракт без подключения к БД |
| `npm run test:db` | Запустить интеграционные тесты в временных схемах указанной БД |
| `npm run db:studio` | Открыть Prisma Studio |

В Prisma 7 генерация клиента и seed выполняются явно. `migrate dev` требует
shadow database и предназначен для среды разработки, где её использование
заранее разрешено. На общей серверной БД используйте `migrate deploy`, а не
`migrate dev`, `migrate reset` или `db push`.

## Если в целевой БД ещё нет таблиц DiceBound

Проверьте `DATABASE_URL` в `.env`, затем:

```sh
npm ci
npm run db:validate
npm run db:generate
npm run db:migrate:deploy
npm run db:seed
npm run db:migrate:status
```

Это создание таблиц в уже предоставленной БД, а не команда создания базы.
История применения хранится в `_prisma_migrations`.

## Переход существующей серверной БД: baseline

По отчёту от 17 октября 2026 года исходные четыре миграции и seed уже были
применены к `dicebound_dev` старым runner. Это исторические сведения;
фактическое состояние сервера необходимо проверить перед переходом.
Следующие действия не выполняются автоматически при запуске приложения.

1. Согласуйте окно изменений, остановите старый runner и сделайте резервную
   копию БД средствами вашей инфраструктуры. Проверьте, что `DATABASE_URL`
   указывает именно на нужную БД и схему (`public` для описанного развёртывания).
2. Сверьте фактическую структуру с четырьмя `migration.sql`: таблицы, типы,
   NULL/default, PK, FK и правила удаления, индексы, CHECK, функции и триггеры.
   Дополнительные `BEGIN` / `COMMIT` в новых файлах не меняют структуру.
   Сверьте встроенные UUID и содержимое seed. Prisma diff не заменяет проверку
   триггеров и CHECK, которые не полностью отражены в Prisma-схеме.
3. Сохраните старую `schema_migrations` как архив вне управляемой Prisma схемы.
   Например, после проверки наличия таблицы, прав и отсутствия конфликта имён:

   ```sql
   BEGIN;
   CREATE SCHEMA IF NOT EXISTS legacy_migrations;
   ALTER TABLE public.schema_migrations SET SCHEMA legacy_migrations;
   COMMIT;
   ```

   Архив остаётся в той же БД. Его не нужно добавлять в шесть бизнес-моделей.
   Схема `legacy_migrations` не должна быть включена в список схем Prisma.
   Не запускайте старый runner после переключения. Если таблицы старой истории
   нет, этот шаг не выполняется.
4. Если `_prisma_migrations` уже существует, сначала проверьте её историю и
   `db:migrate:status`: не удаляйте её и не выполняйте baseline повторно для
   уже зарегистрированных миграций.
5. Только при подтверждённом совпадении всех четырёх миграций зарегистрируйте их:

   ```sh
   npx prisma migrate resolve --applied 001_users
   npx prisma migrate resolve --applied 002_game_systems
   npx prisma migrate resolve --applied 003_characters
   npx prisma migrate resolve --applied 004_character_shares
   npm run db:migrate:status
   ```

   `resolve --applied` записывает историю, но не выполняет SQL и не проверяет
   соответствие таблиц. Если применена лишь часть миграций, отмечайте только
   подтверждённые, затем применяйте оставшиеся через `migrate deploy`.
   При расхождении остановитесь и подготовьте план согласования схемы;
   не маскируйте его через `resolve` и не соглашайтесь на reset.
6. После регистрации совпадающей истории:

   ```sh
   npm run db:migrate:deploy
   npm run db:seed
   npm run db:generate
   ```

   При уже заполненной БД seed проверит данные без обновления дат и содержимого.
   Его ошибка означает необходимость сверки, а не повод удалить старые данные.

## Seed

`prisma/seeds/builtin-systems.json` содержит D&D 5e MVP и Call of Cthulhu MVP,
фиксированные UUID систем и схем и исходный формат `sections -> fields`.
Пользователей, персонажей и историю seed не создаёт.

`prisma.config.ts` запускает `prisma/seed.mjs` через `prisma db seed`.
Скрипт использует существующий драйвер `pg`; дополнительный TypeScript-loader
не нужен. Миграциями по-прежнему управляет исключительно Prisma.

Seed сначала требует успешной регистрации четырёх начальных миграций в
`_prisma_migrations`. Добавление и сверка данных выполняются одной транзакцией.
Повторный запуск не делает UPDATE и не меняет `created_at` / `updated_at`.
Несовпадение опубликованной системы или схемы вызывает ошибку с откатом всего
seed, включая уже сделанные в этом запуске вставки.

## Новые изменения и откат

Изменяйте Prisma-модели и создавайте новую миграцию. Для изменений, которые
нужно дополнить SQL вручную, сначала используйте:

```sh
npm run db:migrate:dev -- --create-only --name <name>
```

Проверьте SQL, добавьте необходимые функции, триггеры и CHECK, затем примените
его в разрешённой среде разработки. Не редактируйте уже применённые файлы;
Prisma хранит их контрольные суммы. Коммитьте схему и SQL вместе.

У Prisma Migrate нет автоматического запуска `down.sql`.
`prisma/manual-rollback/` хранит исходные разрушительные скрипты как справочный
материал; deploy и приложение их не запускают. При ручном разборе зависимостей
порядок обратный: 004, 003, 002, 001. Эти скрипты удаляют таблицы и данные,
не обновляют `_prisma_migrations` и не являются штатной командой отката.
Обычное исправление оформляется новой миграцией; восстановление потерянных
данных требует резервной копии.

Каждая из четырёх начальных миграций явно обёрнута в `BEGIN` / `COMMIT`.
Атомарность действует на одну миграцию, а не на весь запуск deploy:
если следующая упала, предыдущие успешно применённые миграции сохраняются.

## Проверки

`npm run test:seed` проверяет оба встроенных набора и шесть типов полей без БД.
Этот шаг входит в Backend CI.

`npm run test:db` требует явного запуска и `DATABASE_URL`. Тесты создают и
удаляют временные схемы `dicebound_test_<uuid>` в указанной существующей БД;
новую БД они не создают и таблицы `public` не используют. Пользователь БД
должен иметь соответствующие права. Набор проверяет deploy и его повтор,
историю Prisma, seed, ограничения, VIEW/EDIT, restore, удаление оригинала,
soft delete и baseline с сохранением данных. Вызовы CLI направляются только
на временную схему; при обычном завершении она удаляется.

В этой доработке интеграционные тесты и серверный baseline не запускались:
подключение к БД и создание отдельной БД не выполнялись.
