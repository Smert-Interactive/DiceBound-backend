# Реализация регистрации и сессий

Реализованы AUTH-01–AUTH-08 из задания: четыре HTTP endpoint, серверные сессии, защита маршрутов и CSRF, единые ошибки, ограничения попыток, очистка сессий, Swagger и проверки с PostgreSQL.

## 1. Отдельный модуль и общий HTTP bootstrap

**Изменения:** `src/modules/auth/` содержит `AuthController`, `AuthService`, `SessionService` и DTO. `AppModule` подключает `AuthModule`. `configureApp()` настраивает cookie-parser и CORS одинаково в `main.ts` и HTTP-тестах.

**Зачем:** контроллер отвечает за HTTP, `AuthService` — за пользователей и пароли, `SessionService` — за жизненный цикл сессии. Последующие модули смогут использовать общий guard и `request.auth`, не копируя login-логику.

**Альтернативы:** разместить всё в `AppService` или сделать один большой AuthService. Это уменьшило бы число файлов, но связало бы HTTP, пароли и сессии. Отдельные сервисы позволяют проверять срок сессии и cookie независимо от регистрации.

**Выбор пути:** контроллер использует `api/v1/auth`; глобальный prefix не вводился, поэтому `/` и `/health` сохраняют свои адреса.

## 2. Таблица сессий и миграция

**Изменения:** модель `AuthSession`, обратная связь `User.sessions`, новая миграция `005_auth_sessions`. Старые SQL-миграции сохранены. Индексы: уникальный `token_hash`, `user_id`, `expires_at`; внешний ключ удаляет сессии вместе с пользователем.

**Как работает:** login генерирует 32 случайных байта и кодирует их в base64url. В cookie находится исходный токен; в БД — SHA-256, пользователь и дата истечения. TTL фиксированный: 7 дней, без продления на каждом запросе. При повторном login прежняя сессия этого браузера отзывается в той же транзакции, где создаётся новая. Другие устройства остаются авторизованы.

**Почему PostgreSQL:** доступ уже есть, дополнительный сервис не требуется, сессии переживают перезапуск приложения, logout удаляет запись и немедленно отзывает токен для последующих запросов.

**Альтернативы:** JWT потребовал бы дополнительного механизма отзыва для немедленного logout; Redis добавил бы инфраструктуру; память процесса теряла бы сессии при рестарте. SHA-256 подходит для случайного 256-битного токена; для пользовательского пароля используется более дорогой Argon2id.

**Очистка:** раз в час сервис удаляет просроченные строки. Таймер останавливается при закрытии приложения и не держит процесс открытым. Guard отдельно проверяет `expires_at` при каждом запросе: задержка очистки не продлевает доступ.

## 3. Регистрация и проверка входных данных

**Изменения:** схемы Zod и `ZodValidationPipe` реально подключены к `@Body`. Email сначала обрезается по краям и переводится в нижний регистр, затем проверяется. Пароль: 8–1024 символа при регистрации, подтверждение обязательно и должно совпадать. Пароль не обрезается и не меняет регистр. Email ограничен 254 символами.

**Почему такой порядок:** проверка email до `trim()` отвергала бы корректный адрес с случайными пробелами. Верхняя граница пароля ограничивает ненужную нагрузку на хеширование и явно описана в Swagger.

**Хеширование:** установлен `argon2`, явно выбран Argon2id со стандартными параметрами библиотеки и случайной солью. Открытый пароль и подтверждение не сохраняются. Сервер генерирует username вида `player_<случайный суффикс>`; переданный клиентом username не используется.

**Альтернативы:** class-validator добавил бы второй механизм валидации рядом с уже используемым Zod. SHA-256 для паролей слишком быстр для этой задачи. Username из части email был бы предсказуемым и раскрывал бы часть адреса; случайный суффикс этого не требует.

**Дубликаты:** источником истины остаётся уникальный индекс PostgreSQL `lower(btrim(email))`. Prisma P2002 преобразуется в `409 CONFLICT`, в том числе при параллельной регистрации. Предварительный SELECT не используется: он не устраняет гонку и добавляет запрос.

**Результат регистрации:** `201` и публичный User. Cookie и сессия не создаются — это поведение API contract.

## 4. Login, logout и профиль

**Login:** параметризованный `$queryRaw` ищет email по `lower(btrim(email))`, затем `argon2.verify()` проверяет пароль. SQL использует то же выражение, что и существующий индекс, и находит также старые адреса с пробелами и другим регистром. Подстановка пользовательского текста в SQL-строку не применяется.

**Почему не findUnique:** email не является Prisma `@unique`; уникальность задана выражением в PostgreSQL. **Почему не findFirst insensitive:** он учитывает регистр, но не пробелы в старых строках и не повторяет выражение индекса.

Неизвестный email и неправильный пароль получают одинаковые `401` и `Invalid email or password`. Для неизвестного email также выполняется Argon2-проверка по случайному фиктивному хешу, созданному при запуске: это уменьшает различие по времени ответа.

**Cookie:** `dicebound_session`, `HttpOnly`, `SameSite=Lax`, `Path=/api/v1`, 7 дней, `Secure` только в production. Logout удаляет текущую сессию и очищает cookie с теми же параметрами области действия. Отсутствующая/истёкшая сессия на logout возвращает `401`, как и другие защищённые операции.

**Профиль:** `/me` возвращает поля User, число собственных Character (включая независимые EDIT-копии) и число полученных VIEW-доступов. EDIT-доступ не прибавляется к shared-счётчику: его копия уже учитывается как собственный персонаж. Запросы счётчиков выполняются независимо параллельно. Login и me возвращают `Cache-Control: no-store`.

**Защита данных:** запросы регистрации/сессии выбирают разрешённые поля через `select`, а JSON собирается явным маппингом в `snake_case`. Объект с `passwordHash` не возвращается клиенту. Это устойчивее, чем удалять одно секретное поле из полного Prisma-объекта.

## 5. Общая защита маршрутов, CSRF и CORS

**Изменения:** глобальные `CsrfGuard` и `SessionGuard`, декоратор `@Public()`. Публичные маршруты: регистрация, login, `/`, `/health`. Новые Nest-контроллеры требуют сессию по умолчанию. Проверенный пользователь и ID сессии помещаются в `request.auth`.

**Почему глобальный guard:** отсутствие `@UseGuards()` на новом контроллере не должно случайно открыть доступ. `@Public()` снимает только требование сессии, но не проверку Origin.

**CSRF:** все методы, кроме GET/HEAD/OPTIONS, требуют Origin из `ALLOWED_ORIGINS`. Отсутствующий Origin, `null`, чужой origin и похожий домен отклоняются с `403 FORBIDDEN`, до выполнения контроллера. Это относится и к login/register, поскольку login CSRF тоже меняет авторизацию браузера.

**Альтернативы:** отдельный CSRF-токен потребовал бы выдачи, хранения и передачи ещё одного значения. Контракт прямо предусматривает проверку источника, поэтому для текущего браузерного API выбран строгий allowlist. Одного SameSite или CORS для проверки изменяющего запроса недостаточно.

**CORS:** использует тот же явный allowlist, `credentials: true`, без `*`. Preflight обрабатывается до guard. В production список origins обязателен, в development/test по умолчанию разрешены `http://localhost:3000` и `http://localhost:5173`.

**Клиент:** использует `credentials: 'include'`. Для curl/серверных интеграций Origin нужно передавать явно. Разные origin допустимы в пределах совместимой с SameSite=Lax схемы размещения, например localhost с разными портами или поддомены одного сайта. Для полностью разных сайтов текущую cookie-политику нужно пересматривать отдельно.

**Лимиты:** `@nestjs/throttler` ограничивает login до 10, регистрацию до 5 запросов в минуту на IP. Лимит проверяется до хеширования, ответ — `429 TOO_MANY_REQUESTS` с Retry-After. Используется стандартное хранилище процесса: при нескольких репликах понадобится общее хранилище. За reverse proxy необходимо отдельно настроить доверие только к своему proxy; произвольным X-Forwarded-For приложение сейчас не доверяет.

## 6. Единые ошибки

**Изменения:** `AllExceptionsFilter` зарегистрирован через `APP_FILTER`. Production-приложение и тесты получают одинаковые `statusCode`, `timestamp`, `path`, `code`, строковый `message`. Ошибки HTTP не раскрывают произвольные поля объекта исключения. Для всех 5xx клиент получает только `Internal server error`; внутренние детали остаются в серверном журнале.

**Почему APP_FILTER:** прежняя регистрация только в main.ts не распространялась на приложения, созданные через Nest TestingModule. Альтернатива — вызывать регистрацию фильтра в каждом bootstrap; provider устраняет необходимость помнить об этом.

## 7. Проверки

- `test/auth.e2e-spec.ts`: HTTP acceptance с настоящими Nest guards/pipes/filter, cookie-parser, Argon2 и управляемой заменой Prisma. Проверяются регистрация, ошибки данных, дубликат, login, безопасные ответы, me, неизвестная/истёкшая сессия, удалённый пользователь, logout, независимые устройства, ротация, Origin, CORS, защита новых контроллеров, очистка, скрытие внутренних ошибок и отдельные проверки реального rate limiter.
- `src/modules/auth/session.service.spec.ts`: Secure для production, совпадение параметров установки/удаления cookie, точная граница истечения и остановка таймера.
- `src/config/env.schema.spec.ts`: origins, обязательность production-конфигурации, неправильные URL.
- `test/database/auth.postgres.ts`: чистая схема и реальные миграции; гонка регистраций; старый формат email; вход с cookie через supertest.agent; чтение сохранённой сессии новым SessionService; logout; expiry/cleanup; уникальность/FK/индексы/cascade; реальные счётчики VIEW и EDIT.
- `test/database/model.test.mjs`: сохранены существующие проверки модели; число таблиц увеличено, baseline теперь дополнительно проверяет переход с миграций 001–004 на 005 без потери прежних пользователей.

Дополнительно исправлен ESM-путь импорта типа Supertest в существующем `test/app.e2e-spec.ts`: `supertest/types.js`. Без расширения полный `tsc --noEmit` не находил модуль при NodeNext, хотя Vitest и production-сборка проходили.

**Почему два уровня:** HTTP-тесты с заменой БД быстро проверяют маршрутизацию и защиту, но не доказывают корректность SQL и преобразования ошибок Prisma. Интеграционные тесты проверяют реальные индексы, FK и гонки. PostgreSQL-тесты используют случайные схемы, исключают public из search_path и удаляют свои схемы после выполнения; рабочие таблицы не очищаются.

## 8. CI, документация и запуск

Swagger описывает четыре endpoint, DTO, cookie-схему и статусы ошибок. В CI добавлены PostgreSQL 17 и команды `test:db` / `test:auth:db`: успешный HTTP mock-тест больше не является единственной проверкой авторизации.

Перед локальным запуском новой версии:

```bash
npm ci
npm run db:generate
npm run db:migrate:deploy
npm run start:dev
```

В `.env` задаётся `ALLOWED_ORIGINS`, например:

```dotenv
ALLOWED_ORIGINS=http://localhost:3000,http://localhost:5173
```

Миграция 005 подготовлена и проверена в тестовых схемах. Применение к рабочей схеме выполняется отдельно при обновлении backend. Коммит и push в рамках реализации не выполнялись.

Итоговые проверки прошли: `db:generate`, `db:validate`, `lint` без предупреждений,
23 unit/smoke-теста, 32 HTTP E2E-теста, 7 PostgreSQL auth-тестов,
17 проверок модели БД, 5 seed-тестов, `build`, полный `tsc --noEmit` и `git diff --check`.
Изменённый workflow GitHub Actions локально не исполнялся; перечисленные команды выполнены локально.

Frontend после успешного register может выполнить login с теми же введёнными данными и затем перейти на `/characters`: это сохраняет согласованный контракт без автоматического входа на backend.
